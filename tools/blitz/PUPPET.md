# The filtered export

`puppet::export_puppet(g, &mut memo, start)` in Rust, `applyGame(g, blob, knobs, { puppet: { lists, start, rows, ctx, slowTable, vals }, hooks })` in TypeScript. Generated by `puppetgen.cjs` from the schema and `puppet-fields.json`: `puppet.rs`, `bridge/puppet-apply.ts`, `bridge/puppet-lists.json`. Rerun it after the skeleton (build.sh does).

**Format:** `u32` main length, then each of the game's own fields and each `g.m.*` field as a flag and, if the flag is 1, its bytes. Then each table: total, whole-from, entries, byte length, and `row, bytes` per entry. A row at or past whole-from is whole; others are filtered. Then `serial_next` and the loose poses.

- **`start: true`** (a level's start or a load, after the forward export): the long list, every row, and it fills the memo. The rows must already exist in TypeScript.
- **`start: false`**: the every-tick list. A row or field goes only if its bytes differ from what was last sent, compared by bytes.

## Measured

room-clear-four, frames 1200 to 1206, this box. These are numbers on today's tree, where 179 new box rows a tick go whole through the slow path: **don't tune on them until frame boxes land.**

| | |
|---|---|
| Rust export, step | 0.75 to 1.1 ms native release; **not measured in wasm** |
| a step's bytes | 226 KB of about 7.5 MB |
| TypeScript apply, cold | 41 ms, then 10, 9, 8.5, 6.7, 6.2 over the first six ticks |
| TypeScript apply, warm | 3.7 ms median (0.99 the game's own fields, 2.6 rows) |
| of which slow path | 17,000 interpreter reads, nearly all those new box rows |

So about 5 ms on this box, against your budget of 5, and I expect frame boxes to take off most of the rows' 2.6. That's an expectation. The cold start is the JIT and will be visible as a slow first second of a mission unless something warms it.

The warm figure re-applies the same six ticks, so it has no row-making in it and writes less than a first apply would.

## Checked

Every value on the every-tick list equals the whole state, after a start and steps, with long gaps to force new rows:

| mission | frames | values | differ |

| depot-four:1 | 1000, 2000, 4500 | 148,580 | 0 |
| hostage-rescue:2 | 600, 1600, 3000 | 154,893 | 0 |
| snatch-four:1 | 100, 800, 1500 | 132,034 | 0 |

The blobs are real Rust output: TypeScript state imported into Rust, then filtered there. But the Rust game did not step: these are TypeScript's states carried through.

## What it means for readers

- **A changed fixed list gets a new array, in the compiled rows and in the slow path.** A step doesn't visit every holder of a shared array, so an in-place write could reach a row that didn't change (`WallSwitch.pos` did, on hostage-rescue). This replaces constraint 7's "in place" in my earlier message: nothing outside the tick may hold a V3 from a game field across a tick and expect it to move. Whole applies, and `start`, still write in place. Typed arrays stay in place (`jointData` has views into it).
- **A value made during a step has only the listed fields.** A reader that isn't on the list sees `undefined`: `lastStandReport` threw on `st.named` on depot-four, called from tools/qa. So the harness should apply whole states, and any page reader the static list missed will fail like this, loudly. That's the list's real test.
- Fields on the long list but not the every-tick list (`BoxWorld.all`, `Wind.active`) stay as TypeScript's own, which is your one-writer rule.
- `Game.out` isn't here yet: (C).
